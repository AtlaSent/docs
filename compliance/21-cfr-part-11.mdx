21 CFR Part 11 is the FDA regulation governing **electronic records and electronic signatures** in regulated life-sciences environments. When AI agents create, modify, amend, or sign electronic records, Part 11 applies to those actions. Atlasent satisfies Part 11's core requirements through three primitives working together: a deterministic, schema-validated rule engine; an append-only, hash-linked audit chain written before every API response; and tamper-evident permit tokens that serve as the electronic authorization record bound to each action.

## Framework mapping

The table below maps each relevant 21 CFR Part 11 section to the specific Atlasent primitive that satisfies it.

| 21 CFR Part 11 section | Requirement | Atlasent primitive |
|---|---|---|
| §11.10(a) | Validation — system must be validated | Deterministic rule engine with test vectors |
| §11.10(c) | Protection of records — limited access | API key scopes, RBAC roles |
| §11.10(d) | Limiting access to authorized individuals | Evaluation actor identity, policy rules |
| §11.10(e) | Audit trail — secure, computer-generated | Hash-linked, append-only audit chain |
| §11.10(g) | Authority checks — ensure only authorized can use | Permit token + verify-permit endpoint |
| §11.50 | Signature manifestations — identify signer, meaning | Actor ID, action type, decision ID in audit entry |
| §11.70 | Signature/record linking | Decision ID links evaluation, permit, and audit records |

## Permit tokens as audit-level signature equivalents

Under §11.50, an electronic signature must be linked to its record so it cannot be excised, copied, or transferred to another record. Atlasent's permit token fulfills this requirement as follows:

1. The token is a cryptographically signed authorization record containing the agent ID, action type, policy ID, and timestamp. HMAC-SHA256 integrity is enforced at GA today; Ed25519 signing of individual audit entries is available when configured and will become mandatory in a later phase — see the [Security Overview](/trust/security-overview) for current status.
2. The token ID is written into the audit chain at evaluation time — inseparable from the action record.
3. You store the token alongside the record modification in your own system.
4. You can verify the token at any time via `POST /v1/permits/{id}/verify`, which returns a pass/fail result plus the reason code.

<Note>
  The decision ID links the `/evaluate` call, the permit token, and the audit entry into a single attributable tuple. You should store this ID with every record modification your agent makes so that any future inspection can trace the authorization back to the original evaluation.
</Note>

## Starter policy rules

The following JSON policy snippet denies the two operations that would violate §11.10(e) — deletion of records and deletion of audit logs. Import this into your Atlasent policy before any agents operate on electronic records.

```json
{
  "action_type": "audit_log.delete",
  "rules": [
    {
      "id": "deny-audit-log-deletion",
      "condition": {},
      "decision": "deny",
      "deny_code": "DENY_POLICY",
      "message": "21 CFR Part 11: Audit log records cannot be deleted"
    }
  ]
}
```

You should add a matching rule for `ehr.delete` (or the equivalent action type in your system) with the message `"21 CFR Part 11: Electronic records cannot be deleted — §11.10(e)"`.

<Warning>
  If you do not explicitly deny `audit_log.delete` and `ehr.delete` in your policy, Atlasent's fail-closed default applies only to unevaluated actions. Actions that reach the rule engine without a matching deny rule will follow your policy's default decision. Always set your default decision to `deny` for Part 11 workloads and enumerate only the actions you explicitly permit.
</Warning>

## Implementation checklist

Work through the following steps before you put agents into production against regulated electronic records.

<Steps>
  <Step title="Create a scoped API key">
    Create an API key with `evaluate` and `audit` scopes in the Atlasent Console. Do not use a key with broader scopes for agent workloads.
  </Step>
  <Step title="Import the framework preset">
    Import the `21_cfr_part_11` framework preset in the Console under **Policies → Presets**. Review each rule before activating.
  </Step>
  <Step title="Wire protected actions">
    Add an Atlasent `evaluate` call for every operation your agents perform on electronic records — reads, writes, amendments, exports.
  </Step>
  <Step title="Export signed audit bundle">
    At the end of each audit cycle, export a signed audit bundle from **Audit → Export**. The bundle includes all permit and deny decisions with timestamps and actor identifiers.
  </Step>
  <Step title="Verify the bundle">
    Run `atlasent-audit-verify --bundle <path>` to confirm the chain is intact and the signatures are valid before archiving.
  </Step>
  <Step title="Store in your DMS">
    Store the verified, signed bundle in your Document Management System alongside the system validation documentation that lists the Atlasent policy ID and version.
  </Step>
</Steps>
