When a policy returns `hold` or `escalate`, the protected action pauses at a human approval gate. Atlasent's human-in-the-loop (HITL) system manages the full lifecycle of that gate: it notifies reviewers, tracks quorum, records every approval vote in the immutable audit chain, and resolves the escalation once the required approvals are in place. This guide shows you how to create escalations, configure quorum tiers, respond to approval requests, and handle timeouts — with TypeScript and Python examples throughout.

## Hold vs escalate

When your protected call throws `AtlaSentDeniedError`, inspect `err.outcome` to understand what kind of gate you are behind and how to proceed.

| Decision | Meaning | SDK behavior |
|---|---|---|
| `hold` | Paused pending an external condition (time window, async check) | Throws `AtlaSentDeniedError` with outcome `hold` |
| `escalate` | Requires human approval before proceeding | Throws `AtlaSentDeniedError` with outcome `escalate` |

A `hold` typically resolves on its own when a time window opens or an external condition clears. An `escalate` requires a human to explicitly approve or reject before the action can proceed.

## Creating an escalation

When you receive an `escalate` outcome, create an approval request using the `escalations.create` method or the REST API. The escalation links to the original decision via `decision_id` and notifies the reviewers you specify.

<CodeGroup>
  ```typescript TypeScript
  import { AtlaSentClient, AtlaSentDeniedError } from '@atlasent/sdk';

  const client = new AtlaSentClient({ apiKey: process.env.ATLASENT_API_KEY });

  try {
    await client.protect(
      {
        actor: { id: 'user:alice', role: 'deploy_engineer' },
        action: { type: 'production.deploy' },
        target: { id: 'checkout-api', environment: 'production' },
        context: { git_sha: process.env.GITHUB_SHA!, branch: 'main', review_count: 2 },
      },
      async (permit) => {
        await runProductionDeploy();
      }
    );
  } catch (err) {
    if (err instanceof AtlaSentDeniedError && err.outcome === 'escalate') {
      // When you receive escalate, create an approval request
      const escalation = await client.escalations.create({
        decision_id: err.decisionId,
        reason: 'Production deploy requires manual approval',
        notify: ['alice@company.com', 'bob@company.com'],
      });
      console.log('Waiting for approval:', escalation.id);
    }
  }
  ```

  ```python Python
  from atlasent import AtlaSentClient, AtlaSentDeniedError

  client = AtlaSentClient(api_key=os.environ['ATLASENT_API_KEY'])

  try:
      with client.protect(
          actor={'id': 'user:alice', 'role': 'deploy_engineer'},
          action={'type': 'production.deploy'},
          target={'id': 'checkout-api', 'environment': 'production'},
          context={'git_sha': os.environ['GITHUB_SHA'], 'branch': 'main', 'review_count': 2},
      ) as permit:
          run_production_deploy()
  except AtlaSentDeniedError as err:
      if err.outcome == 'escalate':
          escalation = client.escalations.create(
              decision_id=err.decision_id,
              reason='Production deploy requires manual approval',
              notify=['alice@company.com', 'bob@company.com'],
          )
          print(f'Waiting for approval: {escalation.id}')
  ```
</CodeGroup>

### Create escalation via API

```bash
curl -X POST https://api.atlasent.io/v1/escalations \
  -H "Authorization: Bearer $ATLASENT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "decision_id": "dec_01j...",
    "reason": "Production deploy requires manual approval",
    "notify": ["alice@company.com"]
  }'
```

The response includes the escalation ID and current status:

```json
{
  "id": "esc_01j...",
  "decision_id": "dec_01j...",
  "status": "pending",
  "quorum_required": "standard",
  "created_at": "2026-05-01T12:00:00Z"
}
```

## Responding to an escalation

Reviewers can approve or reject an escalation through the Atlasent Console, the Slack bot, or the REST API. A single `reject` is always terminal regardless of how many approvals have accumulated — any reviewer saying "no" closes the escalation immediately.

```bash
curl -X POST https://api.atlasent.io/v1/escalations/esc_01j.../respond \
  -H "Authorization: Bearer $ATLASENT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"response": "approve", "comment": "Reviewed and approved"}'
```

To reject:

```bash
curl -X POST https://api.atlasent.io/v1/escalations/esc_01j.../respond \
  -H "Authorization: Bearer $ATLASENT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"response": "reject", "comment": "Deployment window not yet open"}'
```

## Quorum tiers

Configure the quorum tier when you create an escalation to require multiple approvals before the gate clears. Atlasent counts votes against the configured tier and keeps the escalation in `pending` status until the threshold is met.

| Tier | Required approvers | Use case |
|---|---|---|
| `standard` | 1 approver | Routine deploys |
| `dual` | 2 approvers | Sensitive data operations |
| `emergency` | 1 approver (expedited) | Break-glass scenarios |

```bash
curl -X POST https://api.atlasent.io/v1/escalations \
  -H "Authorization: Bearer $ATLASENT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "decision_id": "dec_01j...",
    "reason": "Customer data export exceeds row cap — DPO review required",
    "notify": ["dpo@company.com", "ciso@company.com"],
    "quorum_tier": "dual"
  }'
```

When an approval vote does not yet satisfy the quorum, the response carries a `quorum_progress` object:

```json
{
  "quorum_progress": {
    "required": 2,
    "approved": 1,
    "rejected": 0,
    "remaining": 1,
    "satisfied": false
  }
}
```

<CodeGroup>
  ```typescript TypeScript
  const result = await client.approveEscalation('esc_01j...', {
    note: 'Verified change-window alignment and DPA reference',
  });

  if (result.escalation.status === 'pending') {
    const p = result.escalation.quorum_progress!;
    console.log(`${p.approved}/${p.required} approvals (${p.remaining} remaining)`);
  }
  ```

  ```python Python
  result = client.approve_escalation(
      'esc_01j...',
      note='Verified change-window alignment and DPA reference',
  )

  if result.escalation.status == 'pending':
      p = result.escalation.quorum_progress
      print(f'{p.approved}/{p.required} approvals ({p.remaining} remaining)')
  ```
</CodeGroup>

## Handling timeouts

Every escalation carries a `timeout_at` value set by your policy's SLA configuration. When an escalation passes its timeout, Atlasent's sweeper automatically applies the `fallback_decision`:

- **`reject` (default)** — the escalation closes as `timed_out` and the linked action is cancelled
- **`approve`** — the escalation closes as `auto_approved` and the action proceeds automatically

The default fallback is **reject** (fail-closed). Only configure `approve` fallback for documented fail-open scenarios.

```bash
curl -X POST https://api.atlasent.io/v1/escalations \
  -H "Authorization: Bearer $ATLASENT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "decision_id": "dec_01j...",
    "reason": "Vendor payment above threshold requires CFO approval",
    "notify": ["cfo@company.com"],
    "quorum_tier": "standard",
    "timeout_minutes": 240,
    "fallback_decision": "reject"
  }'
```

<Note>
  Auto-resolved escalations (`auto_approved` or `timed_out`) produce full audit chain entries attributed to the org owner with a `liability_type` that makes the automated origin unambiguous. They are not treated as human approvals in audit reports.
</Note>

## Audit evidence

Every transition in the escalation lifecycle writes two records:

1. **Audit chain entry** — a tamper-evident, hash-chained record with event types including `hitl.vote_recorded`, `hitl.approved`, `hitl.rejected`, `hitl.timed_out`, and `hitl.auto_approved`
2. **Cross-system timeline entry** — a queryable view that surfaces HITL events alongside permits, connector events, and other audit entries

Audit chain writes are fail-closed: if the chain write fails, the escalation resolution rolls back. Timeline entries are best-effort denormalized telemetry.
