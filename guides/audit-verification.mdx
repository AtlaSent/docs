An Atlasent audit bundle is a hash-chained export of every evaluation, permit, and decision in your organization's history for a given time range. It is designed to outlive the Atlasent service itself — a regulator years after the fact can verify a bundle offline, without trusting Atlasent or the original exporter, using nothing but the bundle file and optionally the public key registry. This guide walks you through exporting a bundle, running verification checks, interpreting failures, and presenting the output to a compliance auditor.

## What verification proves

The audit-verify CLI and SDK helpers check five invariants against every bundle. A bundle passes only if all five hold simultaneously.

1. **Hash chain continuity** — every entry's `previous_hash` matches the prior entry's `entry_hash`
2. **Signature validity** — when Ed25519 signing is enabled, each signature is valid for the public key at that key version
3. **Causal ordering** — sequence numbers are monotonically increasing with no gaps
4. **Completeness markers** — the export bundle includes all entries in the requested range
5. **Canonical form** — entry serialization matches the documented canonical JSON format

A single invariant failure means the bundle cannot be trusted. The verifier reports each invariant independently so you can determine *what* broke, not just *that* something did.

<Warning>
  Never reformat, prettify, or re-serialize a bundle file before verifying it. Any whitespace change, key reordering, or number normalization will change the entry hash values and break chain verification even if the underlying events are intact.
</Warning>

## Export and verify with the CLI

The `atlasent-audit-verify` CLI handles the full workflow in three commands: export, fetch public keys, and verify.

```bash
# Export your audit chain first
curl -X POST https://api.atlasent.io/v1/audit/exports \
  -H "Authorization: Bearer $ATLASENT_API_KEY" \
  -d '{"time_range": {"start": "2026-05-01T00:00:00Z", "end": "2026-05-31T23:59:59Z"}}' \
  -o audit-export.ndjson

# Fetch public keys
curl https://api.atlasent.io/v1/public-keys -o public-keys.json

# Verify
atlasent-audit-verify \
  --input audit-export.ndjson \
  --keys public-keys.json
```

A passing verification prints a summary:

```
✓  audit-export.ndjson
   events=1234  signed_at=2026-05-31T23:59:00Z  key=key_2026q2
   hash_chain=ok  signature=ok  ordering=ok  completeness=ok  canonical=ok
```

### CLI exit codes

| Exit code | Meaning |
|---|---|
| `0` | Verification passed — chain is intact |
| `1` | Verification failed — see output for findings |
| `2` | Input error — file not found or malformed |

Use exit code assertions in CI pipelines to gate compliance checks:

```bash
atlasent-audit-verify --input audit-export.ndjson --keys public-keys.json
if [ $? -ne 0 ]; then
  echo "Audit verification failed — do not proceed with compliance submission"
  exit 1
fi
```

## Offline verification

For scenarios where the Atlasent API is unreachable — a regulator audit years after the fact, an air-gapped compliance review — both SDKs support fully offline verification using only the bundle file and the public key material.

<CodeGroup>
  ```javascript Node.js
  import { readFileSync } from 'fs';
  import { verifyAuditExportBundle } from '@atlasent/sdk';

  const bundle = JSON.parse(readFileSync('audit-export.ndjson', 'utf8'));
  const keys = JSON.parse(readFileSync('public-keys.json', 'utf8'));

  const result = await verifyAuditExportBundle(bundle, {
    trustedPublicKeyPem: keys.keys[0].public_key_pem,
  });

  if (!result.ok) {
    for (const failure of result.failures) {
      console.error(`[${failure.check}] ${failure.subject_id}: ${failure.reason}`);
    }
    process.exit(1);
  }

  console.log(
    `✓ ${result.checks.evaluations} eval rows, ` +
    `${result.checks.envelopes_matched}/${result.checks.envelopes} envelopes matched`
  );
  ```

  ```python Python
  import json
  from atlasent import verify_audit_export_bundle

  with open('audit-export.ndjson') as f:
      bundle = json.load(f)

  with open('public-keys.json') as f:
      keys = json.load(f)

  result = verify_audit_export_bundle(
      bundle,
      trusted_public_key_pem=keys['keys'][0]['public_key_pem'],
  )

  if not result.ok:
      for failure in result.failures:
          print(f'[{failure.check}] {failure.subject_id}: {failure.reason}')
      raise SystemExit(1)

  print(
      f'✓ {result.checks.evaluations} eval rows, '
      f'{result.checks.envelopes_matched}/{result.checks.envelopes} envelopes matched'
  )
  ```
</CodeGroup>

<Note>
  The Python `verify_audit_export_bundle` function requires the `[verify]` extra for Ed25519 signature checking: `pip install atlasent[verify]`. Without it, invariants 1, 3, 4, and 5 still run and the signature check is reported as `signature_unverifiable` rather than a hard failure.
</Note>

## Interpreting verification failures

When verification fails, the output identifies which invariant broke and for which entry. Use this triage guide to determine whether a failure is recoverable.

<CardGroup cols={2}>
  <Card title="Hash mismatch" icon="triangle-exclamation">
    **`chain_integrity_ok=false`, `tampered_event_ids` non-empty**

    The entries listed were edited after signing. The signature may still verify (because the envelope's chain head and event count match), but the event contents do not recompute to their stored hashes. **This is the canonical evidence-tampering shape.** Do not trust this bundle — request a fresh export from the source.
  </Card>
  <Card title="Missing entries" icon="circle-minus">
    **`head_hash_matches=false`, `completeness_ok=false`**

    The bundle was truncated or entries were appended after signing. The chain tail does not match the signed chain head. This may indicate export truncation or post-export modification. Do not trust this bundle — request a fresh export.
  </Card>
  <Card title="Invalid signature" icon="key">
    **`signature_valid=false`, `reason="unknown_signing_key"`**

    The signing key ID in the bundle is not in your local key registry. Atlasent may have rotated its signing key after you cached the registry. Re-fetch `/v1/public-keys` and retry verification. This failure is recoverable.

    If the reason is `signature_mismatch` but chain integrity is intact, the bundle file was reformatted in transit. Ask the exporter to resend the file without piping it through a JSON formatter.
  </Card>
  <Card title="Out-of-order sequence" icon="arrow-right-arrow-left">
    **`ordering_ok=false`**

    Sequence numbers are non-monotonic or contain gaps. This pattern indicates a replay attack or insertion attack — entries were reordered or injected. Do not trust this bundle — treat it as potentially compromised and notify your security team.
  </Card>
</CardGroup>

### Summary: when to request a fresh export

| Failure | Recoverable? | Action |
|---|---|---|
| `unknown_signing_key` | ✅ Yes | Re-fetch public key registry and retry |
| `signature_mismatch` (chain ok) | ✅ Yes | Re-request the original file without reformatting |
| `tampered_event_ids` non-empty | ❌ No | Treat as tampering; request fresh export |
| `head_hash_matches=false` | ❌ No | Treat as truncation; request fresh export |
| `ordering_ok=false` | ❌ No | Treat as insertion/replay; notify security |

## Sharing bundles with auditors

When you hand a bundle to a regulator or external auditor, include three items:

1. The bundle `.ndjson` file, byte-faithful and unmodified
2. The PEM-encoded public key whose `key_id` matches the bundle's `signing_key_id` (pinning to one key removes the registry-fetch step)
3. The SHA-256 digest of the bundle file, delivered on a separate channel (email, PDF, or paper)

The auditor computes `sha256sum audit-export.ndjson` and matches it against your digest before running verification. This out-of-band check catches transit corruption before the verifier even runs.

<Tip>
  Verification is intentionally cross-tenant readable. A regulator holding an API key for any organization can verify a bundle exported by a different organization without that organization's cooperation, as long as the public key registry is accessible. This design means you can hand a bundle to an auditor with no Atlasent access and they can still verify it independently.
</Tip>
