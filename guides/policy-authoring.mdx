Policies are the heart of Atlasent's authorization model. Each policy is a named, versioned collection of rules that map action types to decisions — `allow`, `deny`, `hold`, or `escalate`. You write policies in JSON, import them through the API or Console, and then point your protected action call sites at the resulting policy ID. This guide walks you through the full lifecycle: authoring, naming, importing, versioning, and testing a policy before it reaches production.

## Policy JSON format

A policy document contains an `action_type` binding, an `org_id`, and an ordered array of `rules`. Atlasent evaluates rules from top to bottom and returns the decision of the **first rule whose condition matches**. If no rule matches, the default decision is **deny**.

```json
{
  "action_type": "production.deploy",
  "org_id": "org_01j...",
  "rules": [
    {
      "id": "require-two-reviews",
      "condition": {
        "context.review_count": { "lt": 2 }
      },
      "decision": "deny",
      "deny_code": "DENY_POLICY",
      "message": "At least 2 reviews required before deploying to production"
    },
    {
      "id": "allow-approved-deploys",
      "condition": {},
      "decision": "allow"
    }
  ]
}
```

<Note>
  An empty condition object (`{}`) matches every request. Place catch-all `allow` or `deny` rules last. Rules earlier in the array take precedence — the evaluation stops at the first match.
</Note>

## Rule evaluation order

Rules are evaluated in order from first to last. The first matching rule wins. If no rule matches, Atlasent returns `deny` by default.

1. Exact `action_type` match on the request
2. Prefix wildcard (e.g. `read.*` matches `read.customer.records`)
3. Global wildcard `*`
4. **Default: deny** — if no rule matches, the action is blocked

Always end your rule list with an explicit catch-all rule to make the default behavior visible in your policy document rather than implicit.

## Naming action types

Use lowercase dot-separated segments following the `domain.object.verb` pattern. The action type string must match exactly between your policy file and the string passed to `client.protect()` in your code.

```
production.deploy          ✅ clear, specific
vendor.payment.release     ✅ domain + object + verb
customer.data.export       ✅ domain + object + verb

deploy                     ❌ too generic
ProductionDeploy           ❌ wrong case
production_deploy          ❌ underscores instead of dots
```

## GxP framework presets

Set the `framework` field on your policy to apply a baseline ruleset before your custom rules. GxP baseline rules evaluate first; your custom rules layer on top.

| Preset | Frameworks covered |
|---|---|
| `21_cfr_part_11` | FDA 21 CFR Part 11 |
| `eu_annex_11` | EMA EU GMP Annex 11 |
| `ich_e6_gcp` | ICH E6(R2) Good Clinical Practice |
| `gxp_baseline` | Combined GxP baseline |
| `custom` | Customer-defined rules only |

```json
{
  "name": "Clinical Trial Policy",
  "action_type": "reconciliation.certify",
  "org_id": "org_01j...",
  "framework": "21_cfr_part_11",
  "rules": [
    {
      "id": "require-dual-approval",
      "condition": {
        "context.dual_approval_required": { "eq": true },
        "context.second_approver": { "exists": false }
      },
      "decision": "escalate",
      "message": "Dual approval required — second approver not present"
    },
    {
      "id": "allow-certified",
      "condition": {},
      "decision": "allow"
    }
  ]
}
```

<Tip>
  Start with `gxp_baseline` if you are unsure which specific framework applies. The baseline is conservative and covers common requirements across FDA, EMA, and ICH. You can narrow to a specific preset as your compliance team reviews the rules.
</Tip>

## Import via API

Save your policy to a file and POST it to the policies endpoint. The API returns a `policy_id` that you use to reference this version in your code.

```bash
curl -X POST https://api.atlasent.io/v1/policies \
  -H "Authorization: Bearer $ATLASENT_API_KEY" \
  -H "Content-Type: application/json" \
  -d @policy.json
```

A successful import returns:

```json
{
  "policy_id": "pol_01j...",
  "action_type": "production.deploy",
  "version": 1,
  "status": "active",
  "created_at": "2026-05-01T12:00:00Z"
}
```

## Import via Console

<Steps>
  <Step title="Open the Policies import page">
    Go to **Policies → Import** in the Atlasent Console.
  </Step>
  <Step title="Paste or upload your JSON">
    Paste your policy JSON directly into the editor, or drag and drop a `.json` file.
  </Step>
  <Step title="Validate">
    Click **Validate**. Atlasent checks for syntax errors and conflicting rules before you commit the import.
  </Step>
  <Step title="Import">
    Click **Import**. The Console shows the new `policy_id` and marks the policy as active.
  </Step>
</Steps>

## Versioning and immutability

Policies are **immutable after import**. You cannot edit or delete a published policy version — this is a deliberate compliance control that ensures every permit issued under a policy version can always be traced back to an exact, unchanged rule set.

To update a policy:

1. Author a new policy document with your changes
2. Import it — Atlasent assigns a new `policy_id`
3. Update your code or environment variable to point to the new `policy_id`
4. Old permits issued under the previous version remain valid and verifiable

<Warning>
  Do not delete old policy versions while permits issued under them may still be in flight. The audit chain links every permit to the policy version that authorized it; deleting the version breaks those links for external auditors.
</Warning>

## Dry-run testing

Test your policy before activating it by running `evaluate` calls against it. Use your real actor, action, and context values to confirm the policy produces the decisions you expect.

```bash
curl -X POST https://api.atlasent.io/v1/evaluate \
  -H "Authorization: Bearer $ATLASENT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "policy_id": "pol_01j...",
    "actor": { "id": "user:alice", "role": "deploy_engineer" },
    "action": { "type": "production.deploy" },
    "target": { "id": "checkout-api", "environment": "production" },
    "context": {
      "git_sha": "9f1a2b3c",
      "branch": "main",
      "review_count": 1
    }
  }'
```

A `deny` response when `review_count` is below threshold should look like:

```json
{
  "decision": "deny",
  "deny_code": "DENY_POLICY",
  "message": "At least 2 reviews required before deploying to production",
  "matched_rule_id": "require-two-reviews",
  "policy_id": "pol_01j...",
  "policy_version": 1
}
```

Run dry-run evaluations for each path in your expected-outcomes table before promoting a policy to production use.
