---
title: "POST /v1/verify-permit — verify and consume a permit token"
sidebarTitle: "POST /v1/verify-permit"
description: "Consume a single-use permit before executing a protected action. Returns an error if expired, consumed, or revoked. Every call produces an audit record."
---

After `POST /v1/evaluate` returns an `allow` decision, your system receives a short-lived permit token. You must call `POST /v1/verify-permit` to consume that token immediately before you execute the protected action. This creates a tamper-evident record that links the execution back to the original authorization decision, and ensures that no permit can be silently replayed or reused. Atlasent writes an audit record for every verify-permit call — whether it succeeds or fails.

## Request

**`POST https://api.atlasent.io/v1/verify-permit`**

All requests must include an `Authorization: Bearer` header and a `Content-Type: application/json` header.

### Request body

<ParamField body="permit_token" type="string" required>
  The permit token string returned in `permit.token` from `POST /v1/evaluate`. Tokens are prefixed with `pt_`.
</ParamField>

<ParamField body="actor_id" type="string">
  Optional revalidation field. When provided, Atlasent checks that the consuming actor matches the actor from the original evaluation. If they differ, the request is rejected with `403 forbidden`.
</ParamField>

<ParamField body="action_type" type="string">
  Optional revalidation field. When provided, Atlasent checks that the action type matches the original evaluation. If it differs, the request is rejected with `403 forbidden`.
</ParamField>

### Example request

<CodeGroup>
```bash cURL
curl -X POST https://api.atlasent.io/v1/verify-permit \
  -H "Authorization: Bearer $ATLASENT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "permit_token": "pt_01j8x9y2k..."
  }'
```
</CodeGroup>

## Response

**Status: `200 OK`**

<ResponseField name="valid" type="boolean" required>
  `true` when the permit token is valid, has not expired, and has not been previously consumed or revoked.
</ResponseField>

<ResponseField name="permit_id" type="string" required>
  The stable ID of the permit that was verified (prefix `pt_`).
</ResponseField>

<ResponseField name="status" type="string" required>
  The permit's current lifecycle status after this call: `consumed` on a successful verification, or `expired` / `revoked` if the permit could not be consumed.
</ResponseField>

<ResponseField name="verified_at" type="string" required>
  ISO 8601 timestamp recording when this verification call was processed.
</ResponseField>

<ResponseField name="actor_id" type="string">
  The actor ID from the original evaluation — confirmed to match the consuming actor when `actor_id` revalidation was requested.
</ResponseField>

<ResponseField name="action_id" type="string">
  The action type from the original evaluation.
</ResponseField>

<ResponseField name="expires_at" type="string">
  ISO 8601 timestamp of when the permit would have expired. Useful for audit correlation.
</ResponseField>

<ResponseField name="revoke_reason" type="string">
  Populated (truncated) when `status` is `revoked` — explains why the permit was revoked before it could be consumed.
</ResponseField>

### Example responses

<CodeGroup>
```json Success
{
  "valid": true,
  "permit_id": "pt_01j8x9y2k...",
  "status": "consumed",
  "verified_at": "2026-05-26T10:15:30Z",
  "actor_id": "user_123",
  "action_id": "production.deploy",
  "expires_at": "2026-05-26T10:30:00Z"
}
```

```json Already consumed (409)
{
  "error": "permit_consumed",
  "message": "This permit token has already been consumed",
  "status": 409
}
```
</CodeGroup>

## Error codes

| HTTP status | Error code | Description |
|---|---|---|
| `404` | `not_found` | The token does not exist or belongs to a different organization. |
| `409` | `permit_consumed` | The permit was already consumed. Any replay attempt returns this error. |
| `409` | `permit_expired` | The permit's 15-minute TTL elapsed before it was consumed. Request a fresh evaluation. |
| `409` | `permit_revoked` | The permit was explicitly revoked via `DELETE /v1/permits/{id}` before consumption. |

<Note>
  Permits are strictly single-use. The moment a permit is consumed, the token is invalidated. Any subsequent call with the same token — whether from the same caller or another — returns `permit_consumed`. Build your execution flow so that verify-permit and the action it gates are atomic from your system's perspective.
</Note>

<Note>
  Atlasent writes an audit record for every call to this endpoint, including failed attempts. If a token is replayed, both the original consumption and the replay attempt appear in your audit trail, giving you a complete chain of custody.
</Note>

<Tip>
  Supply both `actor_id` and `action_type` in your verify-permit call to enable server-side revalidation. This provides an additional layer of defence against token misuse in systems where permit tokens are passed through multiple components before consumption.
</Tip>
