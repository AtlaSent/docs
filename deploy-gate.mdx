# The deploy gate step

The deploy gate is the pipeline step of **Production Change Protection**, the AtlaSent Protection Pack for production deploys and infrastructure changes. You can also use it on its own from the developer plans.

The deploy gate places a fail-closed authorization check in front of every production deployment. Before any code reaches production — whether triggered by a human, a CI/CD pipeline, or an AI agent — AtlaSent evaluates the request against your policies and either issues a single-use permit or blocks the action.

**If the evaluation returns anything other than `allow`, the deployment does not run.**

This is different from a CI approval gate. An approval gate checks whether a PR was approved before merge. The deploy gate checks whether _this specific deployment, at this moment, by this actor_ is authorized to execute. The distinction matters for AI agents, after-hours deploys, and high-risk targets.

## The flow

```
CI pipeline / AI agent / human
        │
        ▼
  [POST /v1-evaluate]
        │
        ▼
  AtlaSent policy engine
  (active bundle, versioned)
        │
   ─────┼──────────────────────
   allow│           deny / hold
        ▼                ▼
  permit issued    blocked — action does not run
        │
        ▼
  [POST /v1-verify-permit]
        │
   valid│         invalid / error
        │                └──► blocked — no deploy
        ▼
  deploy executes
        │
        ▼
  audit record (hash-linked, Ed25519-signed)
```

No permit = no deploy. On network error, timeout, or any unexpected response, the action fails closed.

## Setup

### GitHub Actions

```yaml
permissions:
  contents: read
  id-token: write   # production.deploy uses a verified GitHub OIDC workload identity

steps:
  - name: Authorization gate
    id: gate
    uses: Atlasent/atlasent-action@v1
    env:
      ATLASENT_API_KEY: ${{ secrets.ATLASENT_API_KEY }}
      ATLASENT_BASE_URL: ${{ secrets.ATLASENT_BASE_URL }}
    with:
      action: production.deploy
      environment: production
      target-id: ${{ github.repository }}
      context: |
        { "commit": "${{ github.sha }}" }

  - name: Deploy
    if: steps.gate.outputs.verified == 'true'
    run: ./deploy.sh
```

If the policy allows the deployment and the permit verifies, the gate step passes and sets `verified` to `true`. If not, it fails with the denial reason. Gate the deploy step on `verified`, not on `decision`.

The `ATLASENT_API_KEY` secret needs the scopes `evaluate:write`,
`verify:execute`, and `idp_broker:mint`. `production.deploy` runs only under
a verified GitHub workload identity, and `idp_broker:mint` is what lets the
action get one. AtlaSent refuses a key that lacks it with HTTP 403 before
any policy decision, so the deploy never runs. When the policy requires
reviewers, as the self-serve install does, the key also needs
`approval_artifact:mint`: the action mints signed approval evidence from the
pull request's reviews, and without it a deploy with valid approvals stays
blocked. The **Production deploy gate (CI)** key preset in the console
includes all of these. The **Evaluate only** preset from the quickstart does
not. Only an organization admin can grant `idp_broker:mint`. See
[Key scopes](/integrations/github-action#key-scopes) for the scopes
the other modes need.

## What the self-serve install enforces

When you install Production Change Protection from the console, AtlaSent installs one policy for `production.deploy`. You review and authorize it before anything is enforced.

**Reviewers.** At install you choose how many GitHub reviewers each deploy needs: **2** (the default) or **1**, for a team too small to supply two. A reviewer counts only if they approved the pull request on GitHub. The pull request's author never counts, and neither does the person or pipeline requesting the deploy. Choosing 1 is a deliberate trade for small teams. Two independent reviewers is the stronger control, and you can move to it later. AtlaSent never lowers an existing two-reviewer requirement to one.

**Environments.** Keys from the production console are live keys, and a live key is accepted only when the deploy names `prod`, `production` or `live`. Every other value is refused before the policy runs. The `test` and `staging` row applies only to test keys.

| Environment the deploy names | Allowed when |
|---|---|
| `test` or `staging` | The reviewer requirement is met. No time window applies. |
| `prod`, `production` or `live` | The reviewer requirement is met **and** it is Monday–Friday, 09:00–17:00, in the timezone you chose at install. AtlaSent checks the time on its own clock; nothing in the deploy request can satisfy it. |
| Anything else | Denied. |

**A missing approval holds; everything else denies.** A deploy whose only problem is a missing approval is held and sent to an approver instead of being denied outright. Any other failure denies, and the deploy does not run.

**Cancelling a plan doesn't switch protection off.** If a subscription is cancelled or downgraded, existing protected actions keep being enforced exactly as configured. A billing change can withhold new features, never the protection already in place.

## What policies can require

- **Approval count** — minimum number of PR approvals before a deploy is permitted
- **Change window** — restrict deploys to business hours or a scheduled maintenance window
- **Manual approval for high-risk** — route AI-triggered or high-blast-radius deploys to a human reviewer
- **Quorum requirements** — multi-party approval for critical infrastructure changes

See [Policy authoring](/concepts/policy) for the full rule syntax.

## Why this matters for AI agents

AI coding assistants and autonomous agents can trigger deployments. An agent with write access to a CI system can push a commit and trigger a workflow run without a human approving the deploy step.

The deploy gate intercepts that trigger before it reaches production:

```ts
// Inside an AI agent
const decision = await authorize({
  action_type: 'production.deploy',
  actor_id:    'agent:copilot-workspace',
  environment: 'production',
});

if (decision.decision !== 'allow') {
  return `Blocked: ${decision.reason}`;
}
await triggerDeploy();
```

A policy can require `manual_approval: true` for any deploy where the actor is an AI agent, so no agent ships to production unilaterally regardless of what the CI configuration says.

## Audit trail

Every deploy gate call produces a tamper-evident audit record:

| Field | Value |
|---|---|
| `action_type` | `production.deploy` |
| `actor_id` | `ci:github-actions` |
| `decision` | `allow` |
| `policy_bundle_id` | `bndl_abc123` |
| `policy_version` | `v3` |
| `permit_token` | `pt.v4.…` (consumed on verify) |
| `audit_hash` | SHA-256 hash chain |
| `signature` | Ed25519-signed on export |

The chain is append-only and hash-linked, so any change to a recorded decision after the fact is detectable.
