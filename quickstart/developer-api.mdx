## 1. Get a key and seed the demo action

[Create a free account](https://console.atlasent.io/auth/sign-up?utm_source=docs&utm_medium=quickstart) if you don't have one. Then open **API Keys** in the console, click **New Key**, pick the **Evaluate only** preset, and copy the key. It is shown once. Put it in your shell:

```bash
export ATLASENT_API_KEY="ask_live_..."
```

Keys from [console.atlasent.io](https://console.atlasent.io) are **live** keys (`ask_live_...`). The production console does not issue test keys. Keep the key in a secret store, never in examples, source control, or client-side code. [Create an API key](/quickstart/api-key) has the details on scopes.

A live key is accepted only with `context.environment` set to `production`. Any other value (`sandbox`, `test`, `staging`) is refused with `ENVIRONMENT_MISMATCH` before any policy runs, and the refusal is recorded.

Finish the console's setup flow (**Connect my organization**). It seeds a demo `database.execute_sql` action into your organization. That action authorizes nothing real: it returns a decision and executes nothing on its own. It is the safe target for this quickstart.

## 2. Evaluate a protected action

```bash
RESP=$(curl -sS -X POST https://api.atlasent.io/functions/v1/v1-evaluate \
  -H "Authorization: Bearer $ATLASENT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "action_type": "database.execute_sql",
    "actor_id": "dba.alice",
    "context": {
      "environment": "production",
      "sql_text": "SELECT 1",
      "target_database": "analytics",
      "destructive": false
    }
  }')
echo "$RESP" | jq '{decision, permit_token, execution_hash_expected}'
```

The demo policy allows a non-destructive statement from one of its listed DBAs, so this returns `allow` with a Permit. The examples on this page use [`jq`](https://jqlang.org) to read the response.

On `allow` the response carries two values you need at the next step:

- `permit_token`: the signed, single-use Permit (`pt.v4.…`), valid for 1 hour.
- `execution_hash_expected`: the payload hash the Permit is bound to. A Permit issued for `production` must be verified with this exact value, or verification is refused with `PAYLOAD_HASH_REQUIRED`.

The canonical runtime decision is one of `allow`, `deny`, `hold`, or `escalate`.

## 3. Treat the Permit as a bounded execution artifact

If the response requires and includes a Permit, carry that exact artifact to the execution boundary. Do not translate a bare `allow` into permission to execute.

## 4. Verify before the effect

Present the Permit to `/v1-verify-permit` immediately before the effect. Send the same `action_type` and `actor_id` you evaluated, and the `execution_hash_expected` value as `payload_hash`:

```bash
PERMIT_TOKEN=$(echo "$RESP" | jq -r '.permit_token')
PAYLOAD_HASH=$(echo "$RESP" | jq -r '.execution_hash_expected')

curl -sS -X POST https://api.atlasent.io/functions/v1/v1-verify-permit \
  -H "Authorization: Bearer $ATLASENT_API_KEY" \
  -H "Content-Type: application/json" \
  -d "{
    \"permit_token\": \"$PERMIT_TOKEN\",
    \"action_type\": \"database.execute_sql\",
    \"actor_id\": \"dba.alice\",
    \"environment\": \"production\",
    \"payload_hash\": \"$PAYLOAD_HASH\"
  }" | jq '{valid, outcome, verify_error_code, reason, consumed}'
```

A verified Permit returns `"valid": true` and `"consumed": true`. Gate the effect on `valid`, not on the HTTP status: most refusals also return HTTP 200, with `"valid": false` and a `verify_error_code`. Treat any other status, a timeout, or an unreadable body as a refusal too. The **Evaluate only** key preset includes the `verify:execute` scope this call needs.

The Permit is single-use. Run the same verify request a second time and it is refused with `PERMIT_ALREADY_USED`. Evaluate again to get a new Permit.

| `verify_error_code` | What it means |
|---|---|
| `PAYLOAD_HASH_REQUIRED` | `payload_hash` was omitted. Send the `execution_hash_expected` value from the evaluate response. |
| `PAYLOAD_MISMATCH` | `payload_hash` is not the value the Permit is bound to. Send `execution_hash_expected` unchanged. |
| `ACTOR_MISMATCH` / `ACTION_TYPE_MISMATCH` | `actor_id` or `action_type` differs from the evaluate request. |
| `ENVIRONMENT_MISMATCH` | `environment` differs from the environment the Permit was issued for. |
| `PERMIT_ALREADY_USED` | The Permit was already verified and consumed. |
| `PERMIT_EXPIRED` | More than 1 hour passed since evaluate. |
| `MISSING_PERMIT` | `permit_token` was empty. Check that the evaluate response was `allow`. |

**Permit verified does not mean execution happened.** It means the execution gate has established the Permit contract required before the effect. [Verify a Permit](/quickstart/verify-permit) has the full request and response reference.

## 5. Inspect evidence

Open the console. **Decisions** (`/decisions`) lists the evaluation you just made, and **Permits** (`/permits`) lists the Permit it issued. Both read the runtime system of record, not a copy.

Continue to [Audit export](/quickstart/audit-export) to export the decision and verification evidence. Execution/effect is shown only when the applicable observer/provider evidence establishes it.

## Negative tests

Each of these changes one input and must not return `allow`:

- Set `"destructive": true`, or a `sql_text` containing `DROP TABLE` or `TRUNCATE`: `hold`, pending human review.
- Set `"actor_id"` to anything other than `dba.alice` or `dba.bob`: `deny` with `ACTOR_NOT_ALLOWED`.
- Set `"environment"` to anything other than `production`: `deny` with `ENVIRONMENT_MISMATCH`, because the key is live.

<Note>
The demo action executes nothing, so `"environment": "production"` here only matches your live key. Protecting a real production action is a separate step: provision its action class and policy, then follow the controlled customer acceptance process.
</Note>
