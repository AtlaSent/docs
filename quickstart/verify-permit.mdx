<Note>
  If you used [`protect()` / `with_permit()` / `withPermit()`](/quickstart/first-evaluation) on the previous page, the SDK already issued this verify call for you and bound it into the audit chain. **Read this page when you hold a raw permit token** — for example, a permit minted in one service and forwarded to another, or when you want to confirm a permit is still current immediately before a state-changing call.
</Note>

A permit token is not proof of authorization on its own — it's proof of authorization **if and only if** AtlaSent confirms it's current. Verification:

- Rejects tokens that were revoked (for example, policy changed between `/v1-evaluate` and execution).
- Rejects expired tokens (default TTL: 1 hour).
- Verifies the Ed25519 signature.
- Binds this permit to its execution in the audit chain.

## The request

`/v1-verify-permit` is the canonical verifier. Present the `permit_token` together with the `action_type`, `actor_id`, and environment you evaluated, and the evaluate response's `execution_hash_expected` value as `payload_hash`. The key needs the `verify:execute` scope; the **Evaluate only** preset includes it.

```bash curl
curl -sS -X POST "$ATLASENT_API_URL/v1-verify-permit" \
  -H "Authorization: Bearer $ATLASENT_API_KEY" \
  -H "Content-Type: application/json" \
  -d "{
    \"permit_token\": \"$PERMIT_TOKEN\",
    \"action_type\": \"database.execute_sql\",
    \"actor_id\": \"dba.alice\",
    \"environment\": \"production\",
    \"payload_hash\": \"$PAYLOAD_HASH\"
  }"
```

`PERMIT_TOKEN` and `PAYLOAD_HASH` are the `permit_token` and `execution_hash_expected` fields of the `/v1-evaluate` response; the [Developer / API quickstart](/quickstart/developer-api) shows how to capture them. A Permit issued for `production` is refused with `PAYLOAD_HASH_REQUIRED` if `payload_hash` is omitted.

## The response

<ResponseField name="valid" type="boolean" required>
  `true` only when the Permit verified and was consumed. Gate the action on this field.
</ResponseField>

<ResponseField name="outcome" type="string" required>
  `"allow"` on success, `"deny"` otherwise.
</ResponseField>

<ResponseField name="verify_error_code" type="string">
  On `valid: false`, a stable code such as `PAYLOAD_HASH_REQUIRED`, `PAYLOAD_MISMATCH`, `ACTOR_MISMATCH`, `ACTION_TYPE_MISMATCH`, `ENVIRONMENT_MISMATCH`, `PERMIT_EXPIRED`, `PERMIT_ALREADY_USED`, or `MISSING_PERMIT`.
</ResponseField>

<ResponseField name="reason" type="string">
  An operator-readable explanation of the outcome.
</ResponseField>

<ResponseField name="consumed" type="boolean">
  `true` when this call consumed the Permit. A consumed Permit cannot be verified again.
</ResponseField>

<ResponseField name="decision_id" type="string">
  The Decision that issued the Permit, when known.
</ResponseField>

<ResponseField name="expires_at" type="string">
  ISO 8601 expiry of the Permit, when known.
</ResponseField>

Most refusals return HTTP 200 with `valid: false`, so a 2xx status is not authorization. Read `valid`, and treat any other status, a timeout, or an unreadable body as a refusal.

## With an SDK

Use the SDK's execution-boundary helper, [`protect()` / `with_permit()` / `withPermit()`](/quickstart/first-evaluation), so verification happens immediately before the protected effect. If you separate evaluation from execution, use the canonical verification request above at the execution boundary. Do not substitute a permit lifecycle lookup for signature, binding and replay verification.

## When to call verify explicitly

The canonical execution-boundary surface — [`protect()` / `with_permit()` / `withPermit()`](/quickstart/first-evaluation) — already issues this verify call internally and binds it into the audit chain. Reach for the explicit verify call in these cases:

- **Permit crossed a process boundary.** Service A called `evaluate()` and forwarded the unconsumed `permit_token` and its execution binding to service B; B verifies immediately before acting. A permit already consumed by `protect()` cannot be forwarded for reuse.
- **Long-running flow.** Time has elapsed between the policy decision and the state-changing call, and policy or actor state may have moved (e.g. operator revocation, TTL drift). Verify just before execute.
- **You held the permit token after `evaluate()` rather than `protect()`.** The raw `evaluate()` primitive does not verify — callers using it must verify before executing.

Permits are single-use. Once a permit has been consumed, verifying it again returns an error rather than a valid result — a spent permit cannot be replayed.

<Note>
  **Why a separate verify call?** Separating evaluate from verify lets you short-circuit on policy changes that happen between "I got permission" and "I'm doing the thing" — e.g. an operator revoking the permit, or the permit's TTL elapsing.
</Note>
