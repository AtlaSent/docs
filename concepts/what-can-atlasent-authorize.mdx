## AtlaSent authorizes consequential actions before they happen.

**One authorization model can govern deployments, business-system changes,
clinical actions, identity changes, and AI-agent execution.**

The action is authorized against the organization's current rules and evidence,
and the resulting [permit](/concepts/permit) is bound to the exact execution
plan. AtlaSent authorizes **the specific plan about to run** — not the vendor,
not the tool, not "deployments in general."

Each surface below is governed by a **canonical action that already exists**.
Adding a new system of record does not add a new action; it adds context and
evidence on an existing one. The catalog stays small; the plan drives the policy.

## One action, many systems of record

Look closely at the first three cards. **Production Deploy**, **Salesforce
Configuration**, and **NetSuite Financial Configuration** all resolve to the
**same** canonical action — `CANON-000001 · production.deploy`. The interception
point is identical: *execute the authorized change or deployment plan.* A
Salesforce change set and a NetSuite SDF project are change plans, exactly like a
CI/CD release is a change plan. See
Change-plan execution for how one action
covers them all without claiming that every execution is source-code deployment.

## The contract, everywhere

```
request → evaluate → permit → verify → execute → audit
```

Fail-closed. Offline-verifiable proof. The same six-step contract governs a
production deploy, a business-system change plan, a clinical unblinding, an
identity change, and an AI-agent tool call. Start with the
[Runtime flow](/concepts/runtime-flow), or see what a governed change plan looks
like end to end in Change-plan execution.
