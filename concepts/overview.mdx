AtlaSent provides **authorization for consequential computational actions**.
Its core mechanism is **execution-time authorization**: determining whether an
exact consequential action is organizationally authorized under current
conditions before the governed effect occurs.

The distinction to keep in mind throughout these docs is:

> **Verified identity tells AtlaSent who or what is acting. It does not tell AtlaSent what the organization authorizes that Actor to do.**

## The controlled lifecycle

```text
Verified Actor Identity
        ↓
Organizational Authority
        +
Policy + Assertions + required Approval + current Context
        ↓
Evaluation → Authorization Decision
        ↓ allow only, when Permit required
Permit Issued
        ↓
Permit Verification at Gate
        ↓
Native Execution
        ↓
Observed Effect
        ↓
Evidence
        ↓
Verified Proof (only where verification establishes it)
```

This is a semantic ladder, not a claim that every integration exercises every rung. Each stage must remain explicit: `allow` is not a Permit; a Permit is not Verification; Verification is not Execution; Execution is not Effect; Evidence is not automatically Verified Proof.

## Distinctions that must remain intact

- **Identity ≠ Authority**
- **Authority ≠ Authorization**
- **Authority ≠ Approval**
- **Approval ≠ Decision**
- **Decision ≠ Permit**
- **Permit ≠ Verification**
- **Verification ≠ Execution**
- **Execution ≠ Effect**
- **Evidence ≠ Verified Proof**
- **`allow` ≠ Execution**
- **Action Type ≠ Action Class**
- **Action Class ≠ Protected Class**
- **Gate ≠ Policy**
- **Proof ≠ generic log**
