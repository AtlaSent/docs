A policy is a versioned set of rules that Atlasent evaluates every protected action against. You associate a policy with an action type and an org; Atlasent compiles it into an immutable published bundle and loads that bundle on every evaluation request. Because bundles are immutable, you always get a precise answer to "what policy was in effect when this action ran?" — even years later.

## What a policy contains

Each policy targets a single `action_type` (such as `production.deploy` or `ehr.write`) and contains an ordered list of rules. Each rule specifies:

- **`id`** — a stable, human-readable identifier for the rule.
- **`condition`** — a set of field matchers evaluated against the request context.
- **`decision`** — the outcome if the condition matches: `allow`, `deny`, or `hold`.
- **`deny_code`** — the machine-readable code to return when `decision` is `deny` (see [Deny Codes](/concepts/deny-codes)).

```json
{
  "action_type": "production.deploy",
  "rules": [
    {
      "id": "require-two-reviewers",
      "condition": { "context.review_count": { "lt": 2 } },
      "decision": "deny",
      "deny_code": "DENY_POLICY"
    },
    {
      "id": "block-friday-deploys",
      "condition": { "context.day_of_week": { "eq": "friday" } },
      "decision": "hold"
    },
    {
      "id": "default-allow",
      "condition": {},
      "decision": "allow"
    }
  ]
}
```

## Rule evaluation order

The rule engine processes rules from top to bottom and applies a **first-match-wins** strategy:

1. The engine tests each rule's `condition` against the incoming context in the order you defined.
2. When a rule's condition matches, the engine returns that rule's `decision` immediately. No further rules are evaluated.
3. If no rule matches — because every condition failed — the engine returns `deny` by default. This is the fail-closed guarantee: absence of a matching rule is never an implicit allow.

<Warning>
  Order matters. Place your most specific rules at the top (for example, explicit denies and holds) and your broader fallback rules lower down. A catch-all `allow` rule at the top would short-circuit all rules beneath it.
</Warning>

## Immutability and versioning

Policy bundles are **immutable once published**. When you update a policy, Atlasent creates a new bundle version and activates it going forward. The previous bundle version remains queryable.

This gives you two important guarantees:

- Every evaluation decision records the `bundle_id` and `bundle_version` that produced it, so you can reconstruct the exact rule set that was in effect at any point in time.
- Compliance auditors can verify that a policy was not retroactively changed after a decision was made.

<Note>
  Updating a policy does not retroactively affect decisions already recorded in the audit chain. Past decisions always reference the bundle version that was active when they ran.
</Note>

## Policy lifecycle

| Step | What happens |
|---|---|
| **Author** | Write the policy JSON with your `action_type` and rules. |
| **Publish** | POST to `/v1/policies` (or import via the console). Atlasent validates the schema, compiles the bundle, and assigns a `bundle_id` and `bundle_version`. |
| **Activate** | The new bundle becomes the active version for its `(org_id, action_type)` pair. All subsequent evaluations load this bundle. |
| **Update** | Submit a new policy. Atlasent creates a new bundle version. The previous version is retained for audit purposes. |
| **Audit** | Every evaluation decision records `bundle_id` and `bundle_version` in the immutable audit chain. |

## Fail-closed by default

If no published bundle exists for an `(org_id, action_type)` pair when an evaluation arrives, Atlasent returns `deny` with code `NO_ACTIVE_POLICY`. You never get an implicit allow from a missing policy. This default behavior is controlled by `fail_mode: closed` and applies to every action type unless you explicitly override it.

<Tip>
  You can test a policy's evaluation behavior in the Atlasent console before activating it. Use the preview tool to supply sample actor and context values and inspect which rule would match.
</Tip>
